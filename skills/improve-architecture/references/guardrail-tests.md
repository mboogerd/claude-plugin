# Guardrail tests

Architecture rules encoded as tests that fail the build when structure drifts.

Serves two readers: the audit, choosing a mechanism and applying the bar when it
writes a specification; and the ticket that later implements that specification.

## The bar

Encode a rule only when:

- the project already states it as an invariant, or the user has agreed to it
- it is mechanically checkable — no heuristics, no "looks like"
- it is green today, or its violations fit a finite allowlist that is explicitly shrinking

Rules that fail this bar go in the decision log as "considered, not specified", with what would have to be true to specify them later.

Prefer few rules that hold absolutely over many that mostly hold. A suite with routine exceptions trains everyone to add exceptions.

## Amendment policy

Every guardrail test file carries this header, adapted to the language's comment syntax:

```
Architecture guardrails.

Source: [finding id / decision log entry / date]
Enforces: [the invariant, in one sentence]

Amendment policy:
  Adding a rule is always allowed.
  Changing, relaxing, or deleting a rule requires human approval and a note
  in the decision log. A failing guardrail is evidence the change is wrong
  until a human says otherwise — do not edit this file to make a build pass.
```

The last sentence is the load-bearing one: agents fixing a red build will otherwise edit the rule rather than the violation.

## Mechanism by ecosystem

| Ecosystem | Tool |
|---|---|
| JVM (Java/Kotlin) | ArchUnit; Konsist for Kotlin-idiomatic rules |
| TypeScript / JS | dependency-cruiser; `eslint-plugin-boundaries`; ESLint `no-restricted-imports` |
| Python | import-linter; pytest with a custom import walker |
| Go | `go vet` custom analyzer; depguard via golangci-lint |
| Rust | cargo-deny for dependencies; a test walking the module tree |
| Anything | A plain test that walks the source tree and asserts on imports, paths, or names |

The plain-test fallback is usually enough. Reach for a framework when you need cycle detection or layered-architecture assertions, which are tedious to hand-roll.

## Rules that hold up

These are mechanically checkable and rarely need exceptions:

- **Dependency direction** — module A must not import module B (layering, transport neutrality, core purity)
- **No cycles** between packages or modules
- **Boundary types** — public API of a module exposes only types from an approved set
- **Naming to location** — types matching a pattern live in a designated package
- **Annotation or marker consistency** — everything with annotation X also satisfies Y
- **No forbidden dependency** — a library banned by an ADR does not appear outside its sanctioned module

## Rules that do not hold up

Avoid encoding these; they generate exceptions faster than value:

- File or function length limits
- Class count per package
- Anything requiring a judgment of "cohesion" or "responsibility"
- Test coverage thresholds as an architecture rule

## Wiring

The suite runs in the normal test gate, not as a separate optional job — a guardrail that runs only in a nightly job is documentation, not enforcement.

Name the source file so its purpose is obvious in a failure report (`ArchitectureGuardrailsTest`, `test_architecture.py`, `architecture.test.ts`).
